**C-L2 — Low: adapter build caches are unnecessarily partitioned by pipeline identity.**

Evidence: `action.yml:28` includes `${{ matrix.pipeline }}` in the Go build-cache key. Adapter jobs differ by pipeline argument (`pr.yml:113,122–123`), while every invocation builds exactly `./cmd/batz-collector` using `go build -p 1` (`ci/test.py:71`), under the same pinned tools and build settings. The pipeline argument changes collector configuration/native fixtures, not the collector compilation target. There is no remaining per-pipeline Go build tag.

Consequence: adapter identities create separate remote archives for substantially identical compilation work, preventing reuse across adapter identities on later runs in the same PR. On an initially cold run, removing the partition does **not** eliminate concurrent cold builds: both jobs may restore before either saves.

Correction: retain platform/module/job partitioning, remove `${{ matrix.pipeline }}`, and bump the build-cache namespace if the lead accepts this bounded simplification. This follows the actual compiled input boundary; it is independent of simply removing E2E jobs.

Costs and limits: local `ci2-pipeline.log` reports a 2.456-second collector setup, but that is not a hosted saving estimate. The historical hosted adapter jobs spent 36.576 and 46.796 seconds on dependency preparation; these are different source/topology observations, not qualification of a new key.

- Add a collector binary cache: would require additional source/tool/input identity and restore validation, while the present source build is explicit and correct.
- Remove all job partitioning or add broad restore prefixes immediately: possible reuse benefits are unmeasured; different jobs populate materially different cache contents, and exact keys are immutable.
